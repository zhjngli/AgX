# Conceptual Reference Refresh Design

**Date:** 2026-04-25

**Sub-project:** #5 of the [Documentation Initiative](2026-04-06-documentation-initiative-design.md)

## Problem

The "Reference (conceptual)" Diataxis quadrant for AgX is currently three orphan files in `docs/reference/` (`color-spaces.md`, `grain-algorithm.md`, `lut-format.md`) sitting outside the mdbook site introduced by sub-project #1. The mdbook concepts surface (`docs/book/src/reference/concepts/`) is a 3-line placeholder.

Sub-projects #6 (tutorials) and #7 (how-to guides) need a stable conceptual layer to link into — readers learning to "edit your first photo" or "extend a preset" need somewhere to look up *what white balance is*, *how AgX's render pipeline is structured*, or *what a `.cube` LUT actually contains*. Without this layer, tutorials and how-tos either repeat the same concept introductions inline or assume the reader already knows.

The umbrella documentation initiative defined this surface but deferred its content scope to this sub-project's spec.

## Goal

Build the conceptual reference quadrant for AgX so that:

1. Existing `docs/reference/{color-spaces, lut-format}.md` content is relocated into the mdbook site under `docs/book/src/reference/concepts/` and integrated with the rest of the documentation surface.
2. The conceptual layer covers the three areas a curious-photo-nerd or preset-author reader needs: image-processing **foundations** (substrate everything else builds on), **photographic vocabulary** (a lexicon of terms that tutorials and how-tos will cite), and **AgX-specific concepts** (the preset model, render pipeline, and LUT format that aren't covered by general photography references).
3. Every concept page is a stable cross-link target: tutorials, how-to guides, and explanation pages can cite it confidently and the link will not silently break.
4. Cross-links are **bidirectional** between conceptual reference and algorithm explanation: each lexicon entry links forward to the relevant `explanation/` page, and each `explanation/` wrapper page links back to the relevant concept page.
5. The principles that shape this surface are written down in `docs/contributing/documentation-conventions.md` so future doc work follows the same rules without re-litigating the decisions made here.

## Non-goals

- **Tutorials and how-to content** — owned by sub-projects #6 and #7. This sub-project ships only the conceptual layer they will link into.
- **Architectural prose / design-decision narratives** — owned by sub-project #8. The render-pipeline conceptual page covers *what happens to your pixels*, not the architectural rationale for why the pipeline is structured the way it is in code.
- **Re-grouping `explanation/` pages into nested directories.** Sibling `.md` paths under `crates/agx/src/adjust/` would invalidate. `explanation/` keeps its current flat pipeline-order structure.
- **Color-management features** — wide gamut, ICC profiles, log curves are mentioned as future work in `color-spaces.md` but not introduced.
- **Schema reference for the preset format** — auto-generated by `agx-docgen`, owned by sub-project #3. The new `preset-model.md` page covers the *mental model*, not the field-level schema.
- **Migration of `grain-algorithm.md`.** Its content is absorbed by `explanation/grain.md` (sub-project #4) and historical decision rationale already lives in `docs/plans/2026-03-*-grain-*.md`. This sub-project deletes it.

## Audience

Same primary audiences as the umbrella initiative: CLI users and preset authors first, curious photo nerds second. The conceptual reference serves both — preset authors look up vocabulary while building looks; curious photo nerds read the foundations and AgX-specific pages end-to-end.

The "lexicon" pages (Group B below) skew toward the preset-author use case: short entries optimized for cross-linking. The "foundations" and "AgX-specific" pages (Groups A and C) skew toward the curious-photo-nerd use case: longer-form prose with depth.

## Design

### Page list

Nine pages plus a landing index. Three groups, mirroring the audience split.

#### Group A — Foundations (deep)

Substrate that everything else builds on. Not covered anywhere else in the AgX docs.

- **`color-spaces.md`** *(relocate + expand)* — Linear vs sRGB gamma, why each pipeline operation runs in its space, working-space mental model, brief gamut intro, future wider-gamut pointer.
- **`color-models.md`** *(new)* — RGB (additive, physical channels), HSL (cylindrical reframe, why it's useful for selective color edits), luminance (perceptual brightness, weighted sum, what AgX uses for grain weighting and the tone-curve luma channel). Includes a "when AgX uses each model" table.

#### Group B — Photography lexicon (4 small grouped pages)

Per-term short entries, photographer-friendly. Each entry is 2-4 sentences (definition + AgX behavior) with a footer link to the relevant `explanation/` page for math depth. Pages are grouped by photographer-panel mental model (Lightroom / Capture One panel taxonomy), not by pipeline order.

- **`tone.md`** — exposure, contrast, highlights, shadows, whites, blacks, tone curves.
- **`color.md`** — white balance & color temperature, HSL, color grading.
- **`detail.md`** — sharpening, clarity / structure, dehaze, denoise (luminance & chroma).
- **`effects.md`** — grain, vignette.

#### Group C — AgX-specific (deep)

Concepts that aren't covered by general photography references because they're AgX inventions or AgX integrations.

- **`preset-model.md`** *(new)* — Preset = metadata + partial parameters + optional LUT. The `extends` chain (parent composition, override resolution). Why "partial" parameters (none-means-keep-base behavior). Mental model: "preset is a set of overrides on a baseline render."
- **`render-pipeline.md`** *(new)* — Conceptual journey decode → working space → adjustments (in pipeline order) → encode. Where each operation lives and which color space it runs in. Why pipeline order matters (e.g., grain after detail, before vignette). A simple Mermaid diagram of the stages.
- **`lut-format.md`** *(relocate + expand)* — Existing content (what's a LUT, 1D vs 3D, `.cube` format, trilinear interpolation, supported features) plus a new "How AgX generates its bundled LUTs" section: `agx-lut-gen` walkthrough, what each bundled LUT encodes, where they live (`crates/agx-e2e/fixtures/looks/luts/`), how a contributor adds a new generated LUT.

#### Index

- **`concepts/index.md`** *(replace 3-line stub)* — Short paragraph: what conceptual reference is for, who it serves. Three sub-sections (Foundations / Photography lexicon / AgX-specific) listing the nine pages with one-line descriptions each. Footer link to `documentation-conventions.md` for contributors.

### SUMMARY.md structure

The published mdbook sidebar gets the grouped nav. mdbook supports nested entries under a parent, indented in `SUMMARY.md`:

```markdown
# Reference

- [CLI](reference/cli.md)
- [Preset format](reference/preset.md)
- [Concepts](reference/concepts/index.md)
  - [Color spaces](reference/concepts/color-spaces.md)
  - [Color models](reference/concepts/color-models.md)
  - [Tone](reference/concepts/tone.md)
  - [Color](reference/concepts/color.md)
  - [Detail](reference/concepts/detail.md)
  - [Effects](reference/concepts/effects.md)
  - [Preset model](reference/concepts/preset-model.md)
  - [Render pipeline](reference/concepts/render-pipeline.md)
  - [LUT format](reference/concepts/lut-format.md)
```

The grouping (Foundations / Photography lexicon / AgX-specific) appears as visual organization on the `concepts/index.md` landing page, not as additional `SUMMARY.md` levels — mdbook nested headings start to clutter the sidebar past one level of nesting.

### Cross-link contract

The whole point of the conceptual layer is that other surfaces can link into it without breaking. The contract has four directional rules:

1. **Concepts → Explanation (always).** Every lexicon section ends with a `→ See [<algorithm>](../../explanation/<page>.md)` footer line. Foundation and AgX-specific pages link to relevant explanation pages where they exist.
2. **Explanation → Concepts (bidirectional).** Every wrapper page in `docs/book/src/explanation/*.md` (i.e., the page that wraps a sibling `.md` include — not the sibling itself) gets a `## See also` block at the bottom listing relevant concept pages. This is added in this sub-project, including resolving the existing `TODO(sub-project-5)` in `explanation/basic.md`.
3. **Sibling `.md` files stay link-free.** Files at `crates/agx/src/adjust/*.md` contain no cross-`.md` links. The umbrella initiative documents this rule informally; this sub-project formalizes it via the `sibling-md-clean` enforcement check below.
4. **Tutorials / how-tos → Concepts (forward-compatible).** Tutorials and how-tos cite concept anchors directly (`reference/concepts/color.md#white-balance`). This sub-project doesn't ship tutorials but lists the canonical anchors for commonly-cited terms in the conventions doc so #6 and #7 don't have to invent them.

### Single home per concept

Each concept has one canonical defining location. Other pages mention the term and link to its home rather than re-defining. Concrete examples:

- "LUT" is defined in `lut-format.md`. The lexicon `color.md` notes "AgX applies LUTs as part of color grading → see [LUT format](lut-format.md)" but does not define what a LUT is.
- "Linear vs sRGB" is defined in `color-spaces.md`. Other pages reference it by link.
- "Pipeline order" is defined in `render-pipeline.md`. Other pages cite it.

This rule is code-review-only. There is no mechanical enforcement; reviewers verify on PRs that touch `concepts/`.

### Anchor stability

Every entry in the lexicon pages gets a `## <Term>` heading. mdbook auto-generates a `#term` anchor from the heading. Tutorials, how-tos, and explanation pages cite these anchors directly (`reference/concepts/color.md#white-balance`).

Anchor names are part of the public surface of the documentation. Renaming a heading is a breaking change. `mdbook-linkcheck` (already in the `book-linkcheck` step of `verify.sh`) validates fragment identifiers and will fail the build if a heading is renamed and any linker still cites the old anchor. Contributors should also grep `docs/` for the old name to find indirect references.

## Enforcement plan

| Rule | Mechanism | Status |
|------|-----------|--------|
| Anchored cross-links resolve (`page.md#term` exists) | `mdbook-linkcheck` validates fragment identifiers | already enforced via `book-linkcheck` |
| Internal `.md` ↔ `.md` links resolve | `doc-links` regex check in `verify.sh` | already enforced |
| Anchor stability (heading rename + stale linker = build break) | `mdbook-linkcheck` | already enforced |
| Every `explanation/*.md` wrapper page contains a `## See also` block | new `back-links` named check in `verify.sh` | added in this sub-project |
| Sibling `.md` files at `crates/agx/src/adjust/*.md` contain no cross-`.md` links | new `sibling-md-clean` named check in `verify.sh` | added in this sub-project |
| Single source of truth per concept | code review (reviewer checklist) | code review only |
| Per-page depth ceiling | code review (reviewer checklist) | code review only |
| Anchor names match canonical term | code review (reviewer checklist) | code review only |

### New `verify.sh` checks

Two new named checks. Both are short bash blocks following the pattern of the existing `doc-links` check.

**`back-links`** — verifies every wrapper page in `docs/book/src/explanation/` (excluding `index.md`) contains a `## See also` heading.

**`sibling-md-clean`** — verifies no file at `crates/agx/src/adjust/*.md` contains a markdown link of the form `[text](...)`.

Both are wired into the `parallel` matrix in `.github/workflows/ci.yml` so they run as fast standalone CI jobs alongside the existing fast checks.

### Reviewer checklist

For PRs that touch `docs/book/src/reference/concepts/` or `docs/book/src/explanation/` the reviewer ticks:

- [ ] New or changed concept page stays within depth ceiling (1-3 screens, AgX-shaped, links out for theory)
- [ ] No definition duplicates an existing definition elsewhere in the docs
- [ ] Renamed headings: callers updated (or the linkcheck failure is acknowledged and fixed)
- [ ] New lexicon entry placed under the right group (panel-mental-model, not pipeline order)
- [ ] Cross-link footers present (concepts → explanation; explanation → concepts)

The checklist lives in `documentation-conventions.md` so it's easy to find without depending on this dated spec.

## Principles, written down

The decisions made in this brainstorm are captured as durable rules in `docs/contributing/documentation-conventions.md`. Three new sections are added to that doc as part of this sub-project's PR:

1. **Conceptual reference principles** — purpose split (lexicon vs deep dive), lexicon grouping rationale (panel mental model not pipeline), anchor stability, single home per concept, per-page depth ceiling.
2. **Cross-link contract** — the four directional rules above plus the mechanisms enforcing them.
3. **Reviewer checklist for `docs/` PRs** — the operational checklist above.

Discoverability:

- `documentation-conventions.md` itself is the primary home — already cross-linked from `developer-workflow.md` and the umbrella initiative design doc.
- `docs/book/src/reference/concepts/index.md` footer points contributors to the conventions doc.
- `docs/book/src/explanation/index.md` gets the same back-link, framed as the bidirectional contract.
- This spec links to the conventions doc as the live, evolving principle source. The spec captures the *decisions made*; the conventions doc captures the *rules that survive*.

The principles are intentionally **not** placed in `ARCHITECTURE.md` (too granular for that file's audience) or `README.md` (user-facing, not contributor-facing). No new principles file is created — proliferation dilutes discoverability.

## Implementation order

Single PR, sequenced commits. The umbrella initiative confirmed one big PR is acceptable here; the diff is bounded by the page list and the changes are tightly coupled (relocates, new content, cross-link contract, enforcement, conventions all support one another).

1. Move `color-spaces.md` and `lut-format.md` into `docs/book/src/reference/concepts/`. Delete `grain-algorithm.md` and the now-empty `docs/reference/` directory.
2. Replace `concepts/index.md` 3-line stub with the grouped landing page.
3. Write Group A (foundations): expand `color-spaces.md`, write new `color-models.md`.
4. Write Group B (lexicon): `tone.md`, `color.md`, `detail.md`, `effects.md`.
5. Write Group C (AgX-specific): `preset-model.md`, `render-pipeline.md`, expand `lut-format.md` with the bundled-LUT section.
6. Update `docs/book/src/SUMMARY.md` with the grouped concepts nav.
7. Add `## See also` blocks to every `explanation/*.md` wrapper page. Resolves the existing `TODO(sub-project-5)` in `explanation/basic.md`.
8. Add `back-links` and `sibling-md-clean` checks to `scripts/verify.sh`. Wire both into the parallel matrix in `.github/workflows/ci.yml`.
9. Update `docs/contributing/documentation-conventions.md` with the three new sections (principles, cross-link contract, reviewer checklist).
10. Update `docs/backlog/documentation-initiative.md`: tick sub-project #5 and link this design doc.
11. Optional polish: add `## Basic / ## Color / ## Detail / ## Effects` navigation grouping headings to `explanation/index.md` so the conceptual groups exist as cross-link targets in the explanation surface.

## Definition of Done

Mirrors the umbrella `Definition of Done` plus this sub-project's specific gates:

1. `./scripts/verify.sh` passes, including the new `back-links` and `sibling-md-clean` checks.
2. `mdbook-linkcheck` passes for new pages and updated cross-links.
3. `./scripts/e2e.sh` is not required — no editing-pipeline changes.
4. `docs/reference/` directory removed (all three files relocated or deleted).
5. `docs/book/src/SUMMARY.md` shows the grouped Concepts nav.
6. `docs/contributing/documentation-conventions.md` contains the three new sections.
7. Every `docs/book/src/explanation/*.md` wrapper page has a `## See also` block. The existing `TODO(sub-project-5)` in `explanation/basic.md` is resolved.
8. `docs/backlog/documentation-initiative.md` sub-project #5 is ticked and links this design doc.
9. Sub-projects #6 and #7 can cite the canonical anchors listed in the conventions doc without further coordination.
