# Tutorials and How-to Guides Design

**Date:** 2026-04-26

**Sub-projects:** [Documentation Initiative](2026-04-06-documentation-initiative-design.md) — sub-projects #6 (Tutorials) and #7 (How-to guides), brainstormed jointly.

## Problem

The documentation site has Reference and Explanation content live (sub-projects #1–#5, #10, #11), but Tutorials and How-to guides are still stub pages. A new visitor landing on the site cannot answer "how do I install AgX?" or "how do I edit a photo with this thing?" without reading the README, raw rustdoc, or the source. The Reference quadrant assumes the reader has already chosen the tool; the Explanation quadrant assumes the reader is curious about internals. Neither serves the first-time evaluator.

The original backlog framed this as four tutorials (`install`, `first-edit`, `batch-apply`, `multi-apply`) plus five how-to guides. On reflection, that framing misreads the audience: AgX is targeted at photographers who already know Lightroom, Capture One, or Darktable — they understand exposure, shadows, and presets. They do not need a learning-oriented tutorial to teach them what those words mean. They need (a) a fast, trustworthy first-run experience that proves AgX produces real results, and (b) goal-oriented recipes for the production workflows they actually want to run.

## Goal

Ship the Tutorials and How-to quadrants of the AgX documentation site so that:

1. A new visitor can install AgX and edit one photo end-to-end in under ten minutes.
2. A returning user looking up "how do I apply a preset to a folder?" finds a focused, recipe-style answer without scrolling through a learning narrative.
3. Embedded shell commands are protected from silent rot when CLI flags or preset filenames change.
4. The example content (`example/images/`, `example/presets/`, `example/README.md`) is the canonical "try AgX" surface the docs anchor on, and is curated rather than stale.
5. Algorithm explanation pages link forward to the how-to guides that exercise them, completing the bidirectional cross-linking established in sub-project #5.

## Non-goals

- **Bit-for-bit colour matching against other editors.** AgX matches in spirit, not numerics. A "match another editor" how-to is explicitly cut and deferred to a future "Recipes" sub-project framed around genre and look ("for a Portra-style image, lift shadows + cool temperature + add fine grain") rather than coordinate-by-coordinate parity.
- **Genre or look cookbook.** Same reasoning. Future sub-project.
- **Tutorial-grade pixel verification.** The drift-control mechanism asserts commands run successfully; it does not pixel-diff outputs. The e2e suite already pixel-tests preset application and is the right surface for that check.
- **Auto-generated tutorial / how-to content.** Page bodies stay hand-written prose. Only the embedded `example/` artifacts (images, presets) and the CLI reference / preset reference (already auto-generated by `agx-docgen`) are mechanical.
- **An `agx-cli edit` preset-export flag.** A "save your edits as a preset" how-to would be valuable, but the feature does not exist today. Tracked as a feature gap, not a doc gap.
- **Versioned tutorials.** Same constraint as the umbrella documentation initiative: single latest version only.

## Audience

The audience for this sub-project is narrower than the umbrella initiative's full primary list. Tutorials and how-tos serve **CLI users and preset authors who are evaluating or actively running AgX**. The "curious photo nerds" audience is served by Explanation pages (already shipped); contributors are served by the contributing docs and rustdoc. Library consumers do not read tutorials.

The reader's prior knowledge level is "knows what exposure, shadows, and a preset are; has used a GUI photo editor; is unsure whether a CLI photo editor produces results worth the friction." That single assumption shapes every page.

## Information architecture

Three discoverable surfaces, each with a clear job:

| Surface | Job | Quadrant | Page count |
|---------|-----|----------|------------|
| `install.md` | One-line install + verification | Reference (precondition) | 1 |
| `tutorials/getting-started.md` | First-run confidence, mental model of preset + edit | Tutorial | 1 |
| `how-to/*.md` | Recipe per production workflow | How-to | 6 + 1 landing |

Install is a top-level SUMMARY entry, not nested under Tutorials. A reader scanning the left navigation finds it instantly without committing to a tutorial click. The Getting Started tutorial assumes install is done and links back to it on the first line. How-to pages do not link to install — the SUMMARY left-nav entry is sufficient and a per-page reminder becomes boilerplate.

## Sub-project scope shift

The umbrella documentation initiative design doc lists sub-project #6 as "Tutorials" with four pages and sub-project #7 as "How-to guides" with five pages. This brainstorm collapses #6 to a single tutorial and expands #7 by two pages (absorbing the `batch-apply` and `multi-apply` content and dropping "match another editor"):

| Original (#6) | Final |
|---------------|-------|
| Install (tutorial) | `install.md` (top-level page, not tutorial) |
| Edit your first photo with the CLI | `tutorials/getting-started.md` (covers `apply` then `edit`) |
| Apply a look to a directory with `batch-apply` | Moved to how-to: `how-to/batch-apply.md` |
| Compare multiple looks with `multi-apply` | Moved to how-to: `how-to/multi-apply.md` |

| Original (#7) | Final |
|---------------|-------|
| Create your own preset from scratch | `how-to/write-preset.md` |
| Extend an existing preset | `how-to/extend-preset.md` |
| Write and load a custom `.cube` LUT | `how-to/custom-lut.md` |
| Compose layered looks | `how-to/compose-looks.md` |
| Match the output of another preset | **Cut.** Future Recipes sub-project. |

The umbrella design doc's sub-project tables and the `docs/backlog/documentation-initiative.md` checklist are updated to reflect this in the front-door PR (see "PR sequence" below). The cuts and additions are documented in the umbrella doc rather than silently changing scope.

## Tutorial shape

`tutorials/getting-started.md` is one page, layered:

1. **Apply a preset.** Reader runs `agx-cli apply -i <image> -p <preset> -o <out>` against an `example/images/` photo and an `example/presets/` preset. Sees a result.
2. **Tweak with `edit`.** Reader runs the same image through `agx-cli edit -i <image> -o <out> --exposure 0.5 --shadows 30`. Sees a different result. The transition prose explains: a preset is just a saved bundle of these flags.

This sequence — `apply` first, `edit` second — gives the reader instant gratification (one-command magic) before introducing the slider model. It establishes the AgX preset-first mental model in roughly the order a new user encounters the tool: "this thing produces real results" → "and here's how to influence the result."

The page does not attempt to enumerate every adjustment, every flag, or every preset. Two or three adjustments are enough. Readers who want exhaustive coverage have the auto-generated CLI reference one click away.

## How-to shape

Each how-to is a focused recipe for one production task. Pages are short — half a screen of prose, one or two fenced shell blocks, optionally one before/after image pair, a "Variations" section for tasteful alternatives (e.g., `--threads`, output format, recursive directory walks), and a "See also" footer.

The six how-tos:

1. **`how-to/batch-apply.md`** — Apply one preset to every image in a folder via `agx-cli batch-apply -i <dir> -p <preset> -o <dir>`.
2. **`how-to/multi-apply.md`** — Render one image through several presets and compare via `agx-cli multi-apply -i <image> -p preset1.toml,preset2.toml,preset3.toml -o <dir>`.
3. **`how-to/write-preset.md`** — Author a `.toml` preset from scratch, walking through the structure (basic adjustments, HSL, tone curves, etc.) and pointing at the auto-generated preset reference for exhaustive field listings.
4. **`how-to/extend-preset.md`** — Use the preset `extends` mechanism to layer overrides on a base preset.
5. **`how-to/custom-lut.md`** — Write a `.cube` LUT (or generate one with `agx-lut-gen`) and apply it through `--lut`.
6. **`how-to/compose-looks.md`** — Combine layered presets and LUTs in a single render.

`how-to/index.md` is a one-paragraph landing that lists the six recipes with their goal sentences.

## Page templates

Both quadrants use a consistent skeleton, with different voice — narrative for the tutorial, recipe for the how-tos.

### Tutorial template

```markdown
# Getting started with AgX

Assumes AgX is installed — see [Install](../install.md).

(One paragraph: what you'll do, what you'll have at the end.)

## Apply a preset

(Steps. One before/after image pair.)

## Tweak the result with `edit`

(Steps. One before/after image pair.)

## What's next

- [Apply a preset to a whole folder](../how-to/batch-apply.md)
- [Compare looks side-by-side](../how-to/multi-apply.md)
- [Write your own preset](../how-to/write-preset.md)
```

### How-to template

```markdown
# (Goal as a verb phrase)

(One sentence: the goal.)

## Prerequisites

(Bullet list: an installed AgX, sample images, a starter preset, etc.)

## Steps

(Linear, no scenic route. One before/after image pair if useful.)

## Variations

(Optional: alternate output formats, parallelism flags, recursive directory walks.)

## See also

(Links to related how-tos and concept references.)
```

## PR sequence

Three PRs, sequenced:

### PR 1 — Publish prep (`chore: prepare crates for crates.io publish`)

Independent of all doc content. Lands first.

- Audit `Cargo.toml` for `agx` and `agx-cli`: add `repository`, `homepage`, `documentation`, `keywords`, `categories`, `readme`. Confirm `description` and `license` are still accurate.
- Switch `agx-cli`'s dependency on `agx` from `path = "../agx"` to `path = "../agx", version = "0.1"` so cargo uses path locally and the published version when consumed.
- Run `cargo publish --dry-run -p agx`, fix anything it surfaces, publish `agx`. Wait for the index to update. Run `cargo publish --dry-run -p agx-cli`, then publish.
- No `docs/` changes in this PR.

### PR 2 — Front-door (`docs: install page + getting started tutorial`)

Lands the install page, the Getting Started tutorial, and supporting infrastructure.

- New `docs/book/src/install.md` — one-line `cargo install agx-cli`, plus a brief "verify your install" command.
- New `docs/book/src/tutorials/getting-started.md` — replaces the existing `tutorials/index.md` "Coming soon" placeholder, which is deleted in the same commit.
- Updated `docs/book/src/SUMMARY.md` — `[Install](install.md)` as a top-level link before Tutorials; the Tutorials entry repointed from `tutorials/index.md` to `tutorials/getting-started.md`.
- New `scripts/verify.sh` function `check_doc_commands` (see "Drift control" below). Wired into the default check list and into the CI rollup.
- `example/` curation:
  - User-provided replacement / additional images committed under `example/images/`.
  - Optionally one or two new curated presets, drawn from `crates/agx-e2e/fixtures/looks/` if appropriate.
  - `example/README.md` rewritten to match the actual contents (the current file references images that do not exist).
- New `docs/book/src/assets/tutorials/` directory holding the before/after image pair(s) used by the tutorial. Web-sized JPEGs, ~800 px wide, ~80 KB each.
- Updates to `docs/plans/2026-04-06-documentation-initiative-design.md` (umbrella) and `docs/backlog/documentation-initiative.md` (epic): in the umbrella doc, the sub-project `#6` table row is rewritten to reflect "one Getting Started tutorial; install split out as its own top-level page; `batch-apply` and `multi-apply` moved to how-to" with a back-link to this design doc; in the backlog file, `#6`'s checklist entry is rephrased and `#7`'s entry is updated to remove "match another editor" and absorb the two relocated topics. The umbrella doc's open-question and ordering tables are touched only where necessary.

### PR 3 — How-to set (`docs: how-to guides`)

Lands the six how-to pages and the cross-link backfill.

- Six new pages under `docs/book/src/how-to/` (`batch-apply.md`, `multi-apply.md`, `write-preset.md`, `extend-preset.md`, `custom-lut.md`, `compose-looks.md`) plus a one-paragraph `how-to/index.md` landing.
- New `docs/book/src/assets/how-to/` directory holding any before/after pairs for how-to pages.
- `docs/book/src/SUMMARY.md` expanded to list the six how-tos.
- `## See also` blocks added to the relevant `docs/book/src/explanation/*.md` wrapper pages, pointing to how-tos that exercise the explained algorithm. For example, `explanation/dehaze.md` may now point to `how-to/write-preset.md` if that page features `--dehaze-amount`. The `check_back_links` check (introduced in sub-project #5) already enforces presence of a `## See also` block on every wrapper; this PR enriches the contents.
- Updates to `docs/backlog/documentation-initiative.md` checking off `#7`.

PR 2 ships even if PR 3 slips. The result is a half-complete how-to landing for a few days, but a fully working install + tutorial path for new visitors. Any "Coming soon" interim copy in `how-to/index.md` is acceptable for the gap.

## Drift control

Embedded shell commands in `install.md`, `tutorials/getting-started.md`, and the six `how-to/*.md` pages reference live CLI flags, preset file paths, and image file paths. None of those are checked by any existing verify step:

- `check_md_links` validates `[text](path.md)` links to other markdown files.
- `check_book_linkcheck` validates intra-site links.
- `check_external_links` validates outbound URLs.
- `check_markdown_lint` validates style.
- `check_back_links`, `check_sibling_md_clean`, `check_book_no_internal_refs` enforce content boundaries between surfaces.

A renamed CLI flag (e.g. `--exposure` → `--ev`) or a deleted preset file would silently rot the embedded shell blocks without any check failing. The e2e suite uses preset files and would catch a deleted preset, but does not run inline `--exposure 0.5`-style invocations.

### `check_doc_commands`

A new function in `scripts/verify.sh`, following the same pattern as the existing fifteen `check_*` functions:

- Inputs: `docs/book/src/install.md`, `docs/book/src/tutorials/`, `docs/book/src/how-to/`.
- Walks each markdown file, extracts fenced shell blocks (` ```bash `, ` ```sh `, ` ```shell `), filters to blocks that mention `agx-cli` or `cargo run -p agx-cli`.
- For each command line:
  - Substitutes `cargo install agx-cli` → `cargo run -p agx-cli --` so the check works pre-publish and on contributor machines that do not have the published binary installed.
  - Replaces any `-o <output>` path with a tempdir path so the check does not litter the repo or the user's home.
  - Executes the command and asserts exit status 0.
  - Asserts the rewritten output path exists after execution.
- Wired into `scripts/verify.sh`'s default check list and into the `docs-matrix` CI rollup, in the same way `check_doc_links` and `check_back_links` are wired today.

The check is fast — small `example/` images, six or seven invocations total. It does not pixel-diff outputs. The e2e suite is the right surface for that.

## Cross-linking

Documentation surfaces stay loosely coupled, but every surface offers an exit toward canonical reference content. Drift in the prose is bounded because the next click is always machine-checked.

- **Tutorial → reference and explanation.** First mention of any flag in the Getting Started tutorial links to that flag's entry in the auto-generated CLI reference. First mention of "preset" links to the preset model concept page. First mention of "exposure" links to the basic adjustments explanation page.
- **How-to → reference and explanation.** Same pattern. Each how-to's "See also" block lists the relevant concept pages (preset model, render pipeline) and explanation pages (the algorithms the recipe touches).
- **Tutorial → install.** First line of the Getting Started tutorial.
- **How-to → install.** Not linked. SUMMARY left navigation is sufficient.
- **Explanation → how-to (backfill).** PR 3 enriches each `docs/book/src/explanation/*.md` wrapper's existing `## See also` block with a pointer to any how-to that exercises the explained algorithm. For example, `explanation/dehaze.md` may now point to `how-to/write-preset.md` if that recipe features dehaze adjustments.
- **Tutorial / how-to → algorithm explanations.** Each page that touches an algorithm (most do) links to the corresponding `explanation/*.md` page once, in context, the first time the algorithm is mentioned.

The shared `.md` files next to each `crates/agx/src/adjust/*.rs` source remain link-free per the rule established in sub-project #5. Cross-linking happens in the wrapper pages, not the canonical prose.

## Image embedding

Every page that demonstrates a render embeds a before/after image pair near the relevant step. Source images come from the user-curated `example/images/` set (PR 2). Output images are pre-rendered, downsampled to ~800 px on the long edge, encoded as JPEG at quality ~85 (~80 KB each), and committed under `docs/book/src/assets/tutorials/` and `docs/book/src/assets/how-to/`.

Why pre-render instead of regenerating at build time:

- The mdbook build would otherwise need to invoke `agx-cli`, which means the build needs the binary, the example images, and a deterministic render pipeline. The complexity is not worth saving 600 KB of committed assets.
- Asset regeneration only happens when a visible result changes (a preset is retuned, an algorithm changes its output). That is rare. When it does happen, the contributor regenerates the affected pair manually and commits the new JPEG. There is no automation, no CI gate.

The expected total asset count is small: roughly two pairs in the tutorial (`apply` result, `edit` result) and at most one pair per how-to page (six total), for up to sixteen images.

## Open questions

- **Exact how-to ordering in `SUMMARY.md`.** Drafted alphabetically by goal verb in the layout above, but a reading order ("read this one first") may serve better. Decide during PR 3.
- **Whether `how-to/index.md` carries any landing prose beyond a list of links.** Defaulting to "minimal" — just a sentence and the list — but a real one-paragraph orientation may help. Decide during PR 3.
- **Preset filenames featured in the tutorial and how-tos.** Depends on the user-provided image / preset curation in PR 2.

## Success criteria

The sub-project is "done" when:

1. `cargo install agx-cli` succeeds against crates.io.
2. The published docs site has `Install`, `Getting Started`, and six how-to pages live.
3. `scripts/verify.sh` executes every `bash` block in those nine markdown files without error.
4. Every `docs/book/src/explanation/*.md` wrapper page's `## See also` block points to at least one how-to where applicable.
5. `example/README.md` accurately describes `example/images/` and `example/presets/` contents.
6. The umbrella documentation initiative checklist (`docs/backlog/documentation-initiative.md`) has #6 and #7 ticked.
